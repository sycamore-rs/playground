# AGENTS.md

## Project overview

This repository is the online playground for **sycamore-rs**. The frontend is hosted on **GitHub Pages**, and the Rust server is hosted on **Azure Container Apps Express** as a Docker container. They use different origins in production.

## Repository layout

- `client/` — client-side playground code.
- `server/` — Rust/Axum service.
- `shared/` — library crate (`sycamore-playground-shared`) containing API types used by both the client and server, including `CompileRequest`.
- `compilation-env/` — Rust project and build workspace used for compiling submitted playground code to WebAssembly. It is excluded from the root Cargo workspace and not checked into git.
- `artifact-cache/precompiled/` — image-bundled examples (`request.json`, `metadata.json`, `artifact.wasm`, and `artifact.js` per registered example), generated by `--precompile`; ignored by git and preserved at startup.
- `artifact-cache/runtime/` — ephemeral WASM, JavaScript glue, and metadata cache; ignored by git and cleared on server startup.
- `Dockerfile` — multi-stage image build for the server and its WebAssembly compilation environment.

## Development and verification

Run Rust commands from the repository root unless a command explicitly says otherwise:

- `cargo check --workspace` — check workspace crates.
- `cargo check --package sycamore-playground-client --target wasm32-unknown-unknown` — check the browser target.
- Frontend JavaScript dependencies require Node.js 24 and npm (Node is available in `nix develop`). Run `cd client && npm ci` after checkout or dependency changes. Commit `client/package-lock.json`; do not commit `client/node_modules/` or `client/generated/`.
- Trunk's `pre_build` hook runs `npm run build:editor` on each build, bundling `client/js/editor.js` and CodeMirror with esbuild. The hook does not install dependencies. Trunk fingerprints the generated script and watches the JS sources, ignoring `node_modules/` and `generated/` to avoid rebuild loops. To bundle the editor alone, run `cd client && npm run build:editor`.
- Run the backend with `cargo run --package sycamore-playground-server`, then run `cd client && trunk serve` in another terminal. Trunk proxies `/compile` and `/artifacts/` to the backend. The client always displays compilation metadata and, on success with an artifact URL, creates a fresh sandboxed iframe that loads the JavaScript glue and runs the WASM. The iframe permits scripts but not same-origin access; keep these permissions separate so submitted code cannot access the editor.
- `cargo test --workspace` — run workspace tests.
- `cargo build --release` — build the server in release mode.
- `cargo run --package sycamore-playground-server -- --precompile` — compile all examples registered in `server/src/precompiled.rs` into `artifact-cache/precompiled/` and exit. Requires the WASM target. Run offline, not alongside a running server: both modes use the same compilation workspace.

Server logs use `tracing`, writing timestamped, leveled events to stderr. The default level is `info` for the server; set `RUST_LOG=sycamore_playground_server=debug` for cache activity and successful health requests. HTTP logs contain route templates, status codes, and latency, never submitted source, query strings, or full compiler diagnostics.

The runtime compilation environment needs the `wasm32-unknown-unknown` Rust target and `wasm-bindgen-cli` (available in `nix develop`). Keep the CLI version in `Dockerfile` and `flake.nix` aligned with the exact `wasm-bindgen` dependency in `server/Cargo.toml.template`. Compilation runs Cargo offline, then `wasm-bindgen --target web`, and caches the processed `_bg.wasm` together with its generated JavaScript glue. Rebuild existing precompiled bundles with `--precompile` after upgrading from WASM-only bundles. For a fresh local workspace, copy `server/Cargo.toml.template` to `compilation-env/Cargo.toml`, create `compilation-env/src/main.rs` with `fn main() {}`, and run `cargo fetch --manifest-path compilation-env/Cargo.toml` before compiling. Do not filter this fetch by target: offline Cargo resolution can require manifests for target-inactive dependencies, including Sycamore's SSR-only `html-escape`. The Docker image sets this up for the container. Docker builds and container-based sample compilation checks are not required unless explicitly requested.

## Browser testing with Playwright (Pi)

Use the **Playwright MCP server with the Playwright browser extension** to control an approved tab in the user's existing Chromium. This setup has been verified for editing playground code, compiling it, inspecting screenshots, and clicking controls inside the output iframe.

- The MCP server is named `playwright`. Discover its tools through `codemode` using `searchTools(..., { namespace: "mcp__playwright" })` or `describeTool()`, then invoke `tools.mcp__playwright__...`. Do not assume browser tools are declared directly.
- Start with `browser_tabs` (`action: "list"`) and `browser_snapshot` to confirm the selected tab and URL. The extension may ask the user to approve the connection and select a tab. Do not access unrelated tabs.
- The deployed playground is `https://play.sycamore.dev/`. To verify repository changes, use the local Trunk URL instead (normally `http://localhost:8080`), with the backend and Trunk running as described above. Testing the deployed site does not test un-deployed changes.
- Use fresh accessibility snapshots to obtain element references before filling the Rust code textbox or clicking Run. After compilation, inspect the metadata and wait for the output iframe to finish loading. Interact with controls inside the iframe and verify the resulting state, not just compilation success.
- For visual work, take screenshots with `browser_take_screenshot` and actually view the returned images. In codemode, forward image content blocks with `image(block)`; a screenshot path alone is not visual verification. Check relevant desktop/mobile layouts and loading/error states.
- HTTP 408 means the server's five-second compilation timeout was exceeded. A single retry may succeed after a cold build warms the compilation workspace; report persistent failures rather than retrying indefinitely.
- Prefer this long-lived MCP connection over launching `playwright-cli open` through sandboxed Bash. The installed Linux `pi-sandbox` runtime creates a per-command PID namespace, so browser daemons started there do not reliably survive between tool calls. Do not disable or weaken the sandbox to work around this.
- MCP browser control is separate from the Bash sandbox's restrictions. Keep manual extension approval enabled and prefer a dedicated development browser profile. Do not change user-level permissions or browser configuration without approval.

### User setup / troubleshooting

Install the official [Playwright Extension](https://chromewebstore.google.com/detail/playwright-extension/mmlmfjhmonkocbjadbfplnigmagldckm) in Chromium. From a normal terminal, register the server with `pi mcp add playwright -- npx -y @playwright/mcp@latest --extension`. In `~/.pi/agent/mcp.json`, set the server's `env.PLAYWRIGHT_MCP_EXECUTABLE_PATH` to the user's Chromium executable (find it with `command -v chromium`). This MCP setting is independent of the CLI wrapper in `flake.nix`; without it the extension integration may incorrectly look in Google Chrome's profile directory. No global npm installation is required.

Run `/reload` and inspect/reconnect the server through `/mcp`; restart Pi if needed. Keep browser-profile tokens and other machine-specific credentials out of this repository.

## Frontend backend URL configuration

- The frontend reads `BACKEND_BASE_URL` at compile time using `option_env!()`. Unset or empty means same-origin requests (`/compile`), preserving the local Trunk proxy workflow. A trailing slash is allowed; the frontend appends `/compile` to the base URL.
- Set the GitHub Actions repository variable `BACKEND_BASE_URL` to the Azure backend's HTTPS base URL (for example, `https://your-app.azurecontainerapps.io`, without `/compile`). `.github/workflows/deploy.yml` passes it into the frontend build environment. Rebuild and redeploy the frontend after changing it; it is not a runtime setting or a secret.
- The public backend supports uncredentialed cross-origin requests (`Access-Control-Allow-Origin: *`), including JSON POST preflights. This also allows artifact loads from the sandboxed iframe's opaque origin. Trunk's proxy applies only during local development.

## Implementation notes

- Keep server changes in `server/`; its manifest is `server/Cargo.toml`.
- Define types shared by the frontend and backend in `shared/src/lib.rs`, rather than duplicating them. API request types should support both Serde serialization and deserialization, with public fields where needed by consumers.
- `POST /compile` accepts a shared `CompileRequest` and returns JSON `CompileResponse` metadata (artifact URL, original compilation duration, structured warnings, and cache-hit status). `GET /artifacts/{hash}.wasm` serves processed WebAssembly and `GET /artifacts/{hash}.js` serves its matching ES-module glue; missing artifacts return 404 and clients should resubmit the compile request. Preserve the health endpoint. Artifact downloads negotiate Brotli (`Content-Encoding: br`) through a route-scoped `tower-http` compression layer at quality 4, with `Vary: Accept-Encoding` and uncompressed fallback. Compression happens during delivery; cached files remain uncompressed. Compile and health responses are not compressed by this layer.
- Compilation uses the shared `compilation-env/` workspace and is serialized by a lock. Check the artifact cache before and after acquiring the lock; publish an independent artifact copy before releasing it.
- Deployment currently scales to at most one instance. Use a simple local, ephemeral artifact cache; do not add shared storage or replica-routing infrastructure for now. Request hashes include a random startup namespace; no explicit environment version is needed. Revisit artifact storage if multiple replicas are enabled.
- Cache limits are configured with `ARTIFACT_CACHE_MAX_BYTES` (default 512 MiB) and `ARTIFACT_CACHE_MAX_ENTRIES` (default 1,000). Evict least-recently-used unpinned entries, protecting artifacts for five minutes after each compile response references them. Successful compilations only are cached. The Dockerfile runs the server binary with `--precompile` during the image build. Startup registers bundled artifacts as pinned entries referencing their files directly, without compiling or copying WASM. Bundled metadata contains duration and warnings, not runtime URLs or cache-hit flags. A missing bundle is allowed in local development (lazy compilation); an incomplete or stale bundle fails startup. Size limits must leave room for the pinned example plus other artifacts, and disk needs headroom for staging and the compilation workspace.
- A full cache returns 503 with `Retry-After` rather than evicting protected artifacts. At most eight HTTP cache-miss requests may be running/queued; additional misses return 429 with `Retry-After`. Cache hits bypass this admission limit.
- Compilation is not a security sandbox: submitted Rust can read compiler environment variables and filesystem contents at compile time. Do not expose secrets to the compilation process; stronger isolation is needed before treating it as a secure untrusted-code service.
- `server/src/compiler.rs` owns compilation and diagnostic parsing for both HTTP requests (five-second timeout) and offline precompilation (five-minute timeout per example). Keep these paths aligned.
- Keep the Docker build aligned with the Rust toolchain, server dependencies, and targets needed both to run the service and compile WebAssembly. The builder stage must copy `shared/` along with the client and server workspace crates.
- Do not commit generated build output such as `target/` directories or environment-specific secrets.
